# v0 Frontend App

Create production-quality frontend apps with Vercel v0 by composing a strong, structured prompt and then driving the gateway tools (`create_app`, `send_app_message`, `get_app_preview`) — all pinned to `provider="v0"`.

This skill is the right tool when the user wants a *UI artifact*: a web app, dashboard, portal, landing page, internal tool, marketing page, or React/Next.js component. It is **not** for backend services, AI agents, n8n workflows, or BTP/CAP extensions.

## When to Use This Skill

**Both** conditions must be met:

1. The Vercel gateway tools (`create_app`, `send_app_message`, `get_app_preview`) are available in the current environment.
2. The user **explicitly** asks to create an app with **Vercel** or **v0**.

Do **not** use this skill when:

- The user asks for a generic "frontend app", "web app", "dashboard", etc. without mentioning Vercel or v0 → use the `intent-analysis` → `prd-to-spec` → `spec-to-code` chain instead.
- The user wants an **AI agent** → use `sap-agent-bootstrap` / `create-agent-extension`.
- The user wants a **workflow / automation** → use `n8n-workflow`.
- The user wants a **BTP extension / CAP service / Fiori app** → use the `intent-analysis` → `prd-to-spec` → `spec-to-code` chain.
- The user wants **simple static files or scripts** → use the file tools directly.

## Prerequisites

- The host agent (e.g. webagent) must expose the **gateway tools**: `create_app`, `send_app_message`, `get_app_preview`. These ship with `@sap/webagent`'s `gatewayToolModule`. If they are not registered, stop and tell the user the host environment does not support v0 generation.
- A backend reachable at the configured `apiBaseUrl` that proxies to the v0 gateway (`POST /gateway/v0/create-app`, `POST /gateway/v0/send-message`, `GET /gateway/v0/preview/:projectId`, `GET /gateway/v0/files/:projectId`).
- The user has accepted that the app will be generated by an external provider (Vercel v0) and that files will be synced back into the current webagent project.

## Tools

Always pass `provider="v0"`. Do not ask the user which provider to use — this skill is v0-only.

| Tool | When to call | Notes |
|------|--------------|-------|
| `create_app` | Once per solution, after clarifying questions, to scaffold the initial app. | Required: `provider="v0"`, `prompt`. Optional: `project_name` (auto-generated if omitted), `solution_id` (see below), `prd_files` (see below). On success, the webagent project context is switched to the new v0 project. |
| `send_app_message` | For every follow-up change the user requests. | Required: `provider="v0"`, `message`. `project_id` defaults to the current project. After each call, files are synced back automatically (best-effort). |
| `get_app_preview` | When the user asks "where can I see it?", or after a meaningful change, or to confirm the preview URL. | Returns `null` if no preview is available yet — surface that clearly. |
| `ask_question` | To collect the clarifying answers in Step 1. | Use the host's question proxy. Prefer batched questions over a long back-and-forth. |

Do **not** use `write_file` / `update_file` / `execute_command` to hand-edit a v0-generated app. v0 owns the source of truth — round-trip changes through `send_app_message` so the provider stays in sync. The only exception is small post-processing (e.g. patching a config the user explicitly asked for that v0 cannot do).

### Choosing the right tool: `create_app` vs `send_app_message`

Always check first whether the current solution already has a v0 app:

- **Solution already has a v0 app** (chat history references a v0 project, or `get_app_preview` returns a non-null URL) → use `send_app_message`. Do **not** call `create_app` again — it would attach a *second* v0 project to the same solution and the user's chat would diverge across two projects.
- **Solution has no v0 app yet** → use `create_app`.

### `solution_id` parameter — what to pass

Default behaviour: **omit `solution_id`**. The host (`@sap/webagent`) auto-fills it from the current project context, so the new v0 app attaches to the solution the user is already working in. This is what you want 99% of the time.

Pass `solution_id` explicitly only when:

- The user has explicitly asked you to scaffold a v0 app for a *different* solution they own (rare).
- You are running outside any project context (very rare — most agent invocations are inside a project).

Never invent or guess a UUID. If unsure, omit the parameter and let the host default kick in.

### Attaching a PRD with `prd_files`

`create_app`'s `prompt` is forwarded to v0's `description` field, which v0 caps at **1000 characters**. A long PRD will overflow that limit. Use the `prd_files` parameter to attach existing solution-version files (e.g. `docs/PRD.md`, `docs/spec.md`) as project context instead — AGG fetches the content from the backend on the user's behalf and seeds the v0 chat from those files before the prompt drives scaffolding.

Use `prd_files` when **any** of these is true:

- A PRD or spec file already exists in the current solution (e.g. produced by `product-requirements-document` or `specification` skill).
- The user explicitly asks to "use the PRD" or "build from this spec".
- The combined intent + screens + data description would exceed ~800 characters in a single `prompt`.

Keep `prompt` short and directive when `prd_files` is set — typical shape: `"Scaffold a Next.js app from the attached PRD. Use Tailwind + shadcn/ui."` — v0 will treat the files as the source of truth and the prompt as a directive.

Pass `prd_files` as an array of paths relative to the solution version, e.g.:

```
create_app({
  provider: "v0",
  prompt: "Scaffold a Next.js app from the attached PRD.",
  prd_files: ["docs/PRD.md"],
})
```

If no PRD/spec file exists in the project, omit `prd_files` and put the full description in `prompt` (subject to the 1000-char limit).

## Workflow

### **MANDATORY: Setup the Solution**

Before calling `create_app`, run the `setup-solution` skill to scaffold `solution.yaml` and `assets/<asset-name>/asset.yaml`. The v0 app must live as a `vercel-app` asset inside the solution so that Joule Studio runtime's deployer can pick it up — Joule Studio runtime's deployer supports `vercel-app` natively.

The generated `assets/<asset-name>/asset.yaml` MUST conform to the canonical schema at [`../setup-solution/assets/vercel-app.json`](../setup-solution/assets/vercel-app.json) and look like this:

```yaml
apiVersion: asset.sap/v1
kind: Asset
metadata:
  name: <kebab-case-name>
  version: 1.0.0
type: vercel-app
container:
  buildPath: src
  port: 5000
```

Pinned values for v0:

- `type: vercel-app` — required for Joule Studio runtime's deployer to route the asset.
- `container.buildPath: src` — v0-synced files are placed under `assets/<asset-name>/src/` (the gateway's file sync writes there). Do NOT use `.` as `buildPath` for v0 apps.
- `container.port: 5000` — the port the v0 Next.js app listens on inside the container. Do not change unless the user has a hard requirement.
- `metadata.name` — kebab-case, matches the directory name under `assets/`.

If `setup-solution` produces a different shape (e.g. `buildPath: .`), correct it to match the pinned values above before proceeding.

### Step 1: Clarify the request (MANDATORY before generating)

Before calling `create_app`, gather the inputs that make a v0 prompt strong. Use `ask_question` (one batched question with multiple sub-points is fine) and skip any item the user already answered in their original request.

Ask about:

1. **Purpose** — What is this app *for*? What problem does it solve? (1 sentence)
2. **Primary users** — Who uses it, in what context (desktop / mobile, work / consumer, technical / non-technical), and what decision or action are they trying to make?
3. **Key screens & components** — List the actual screens, sections, and widgets (e.g. "landing hero, pricing table with 3 tiers, FAQ accordion, contact form" or "dashboard with KPI cards, revenue line chart, recent orders table, filter sidebar").
4. **Data** — What data does each screen show? Real data source, mock data, or placeholder? If real, what shape (fields)?
5. **Stack & libraries** — Default to **Next.js (App Router) + React + Tailwind + shadcn/ui** unless the user specifies otherwise. Confirm if the user has a preference (Vue, plain React, framer-motion, react-three-fiber, etc.).
6. **Design taste & constraints** — Visual tone (minimal / playful / corporate / dark / brand colors), layout density, mobile-first vs desktop-first, accessibility requirements, anything to *avoid*.
7. **Project name** — Optional. Suggest one (`<short-purpose>-app`) and let the user override.

**Fast path:** If the user's original message already covers purpose + components + stack, skip the question and jump straight to Step 2 — but always echo back your understanding in one short paragraph before generating, and ask for a yes/no confirmation.

### Step 2: Compose the v0 prompt

Build a single prompt string for `create_app` using the **Product Surface / Context of Use / Constraints** framework. v0 generates dramatically better output (faster, fewer lines, fewer placeholders) when all three are explicit.

Use this template:

```
Build a <app type> called <name>.

Purpose: <one sentence>

Users: <who, where, on what device, what decision/action>

Screens & components:
- <screen 1>: <components, data shown, key actions>
- <screen 2>: <components, data shown, key actions>
- ...

Data: <real source / mock / placeholder, with field shapes if known>

Stack: <Next.js App Router + React + Tailwind + shadcn/ui by default>
Libraries: <only if requested, e.g. framer-motion for transitions, recharts for charts>

Design:
- Tone: <minimal / playful / corporate / etc.>
- Layout: <card-based / sidebar + main / single-column / etc.>
- Color: <brand colors or palette guidance>
- Responsive: <mobile-first / desktop-first>
- Accessibility: <WCAG AA, keyboard nav, etc., if relevant>

Do not: <things to avoid — placeholder Lorem Ipsum, fake auth, etc.>
```

Keep the prompt concrete. Replace generic words ("a dashboard") with specifics ("a sales dashboard with 4 KPI cards: MRR, new customers, churn rate, NPS").

### Step 3: Create the app

Call `create_app` exactly once:

```
create_app(
  provider="v0",
  prompt=<the composed prompt>,
  project_name=<optional, e.g. "sales-dashboard-app">
)
```

After the call:

- The result includes a `projectId` and (often) a `previewUrl`. The webagent project context is automatically switched to the new project.
- Tell the user: project created, project name, and the preview URL if present. If `previewUrl` is `null`, say so and explain that a preview will be available once v0 finishes the first generation — they can ask for it again with `get_app_preview`.

### Step 4: Iterate with send_app_message

Every follow-up change goes through `send_app_message` with `provider="v0"`. Examples:

- "Add a dark mode toggle in the top right"
- "Replace the bar chart with a line chart and add a 30-day moving average"
- "The pricing table needs a 4th tier called Enterprise with a 'Contact us' button"

Guidance for follow-ups:

- **Functional / structural changes** (new components, new data, new behavior, layout changes) → use `send_app_message`. v0 will edit files and the gateway will sync them back into the project.
- **Pure visual tweaks** (colors, spacing, font size) → still go through `send_app_message`, but tell the user that for fine-grained design work the v0 web UI's Design Mode is faster than prompting.
- **One change per message** when the user gives a list — it lets v0 stay focused and produces cleaner diffs. Batch only when changes are tightly coupled.
- After each call, mention how many files were synced back (`filesSynced` in the result) and the updated preview URL if changed.

### Step 5: Share & verify the preview

- When the user asks where to see the app, or after a meaningful iteration, call `get_app_preview(provider="v0")` and surface the URL.
- If `url` is `null`, tell the user the preview is not ready yet rather than making one up.

## Prompt Quality Checklist

Before sending to `create_app`, the prompt should answer:

- [ ] **What** is being built (app type + name)?
- [ ] **Why** (one-sentence purpose)?
- [ ] **Who** uses it and in what context?
- [ ] **Which screens/components** with real names, not "etc."?
- [ ] **What data** is shown (real shape, mock, or placeholder)?
- [ ] **Which stack & libraries** (default to Next.js + React + Tailwind + shadcn/ui)?
- [ ] **Design tone & layout** (concrete, not "modern")?
- [ ] **Constraints** ("do not invent auth", "no placeholder text", etc.)?

If any box is empty and the user has not explicitly waived it, ask before generating.

- Be direct. One short clarification round, then build.
- Always echo back your understanding (1–3 lines) before calling `create_app`.
- Report `projectId` and preview URL after every state change.
- Never claim a preview URL exists if `get_app_preview` returned `null`.

## Examples

### Example 1: Vague request → clarify, then build

**User:** "Build me a frontend app for tracking my reading list."

1. Ask one batched question covering: (a) screens (list, detail, add form?), (b) data (just title/author, or also rating, notes, tags?), (c) personal use vs shareable, (d) stack preference, (e) design tone.
2. Compose a prompt with the answers and call `create_app(provider="v0", prompt=…, project_name="reading-list-app")`.
3. Report the preview URL.

### Example 2: Specific request → build immediately

**User:** "Build a Next.js + Tailwind + shadcn landing page for a SaaS called Pulse: hero with email signup, 3-tier pricing table, FAQ accordion, footer. Brand color emerald. No placeholder copy — write real marketing copy aimed at engineering managers."

1. Echo understanding in 2 lines, ask "Proceed?" (yes/no).
2. Call `create_app(provider="v0", prompt=…, project_name="pulse-landing")` with the request reformatted into the Product Surface / Context / Constraints template.
3. Report preview URL.

### Example 3: Follow-up iteration

**User (after the landing page is up):** "Add a customer logos strip below the hero, and change the pricing CTA on the top tier to 'Start free trial'."

1. Call `send_app_message(provider="v0", message="Add a customer logos strip below the hero (6 placeholder logos in a responsive grid). Change the pricing CTA on the top tier from its current text to 'Start free trial'.")`.
2. Report files synced and updated preview URL.
