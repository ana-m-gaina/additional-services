## Product Purpose & Value Proposition

**Elevator Pitch:**  
CDMs spend hours every week hunting through spreadsheets, emails, and PDFs to answer one question: "Is this chargeable, what does it cost, and has it been invoiced?" This agent puts every answer one message away and automates the invoicing trail.

**Business Need:**  
SAP Customer Delivery Managers have no single workspace to look up R&R chargeability, confirm pricing, manage the AS request lifecycle, generate O2I JIRA tickets, or process OPS meeting notes. Work is scattered across manual tools with no audit trail, causing missed invoicing steps and slow customer response times.

**Expected Value:**  
- Eliminate manual lookup time for R&R and pricing (currently 15–30 min per query)
- Reduce missed O2I invoicing steps through agent-driven ticket generation with explicit CDM confirmation
- Provide a full audit trail of AS requests, decisions, and owner changes via persistent CAP OData storage
- Enable meeting notes to be processed in minutes rather than hours, with structured output ready for DED Weekly Status

**Product Objectives (Prioritized):**
1. Joule Studio deployment readiness — agent passes UMS discovery, deploys on BTP, and is governed under Joule runtime standard
2. Full tool coverage — all 20 tools in the existing orchestrator are correctly described, discoverable, and testable via MCP artifacts
3. Observability — all 7 business milestones are instrumented with OTel spans and structured log statements
4. Eval coverage — all 7 skills have aeval test cases; no skill ships without a test

## User Profiles & Personas

### Primary Persona: The CDM (Customer Delivery Manager)

A mid-senior SAP delivery professional managing 5–15 active customer accounts. Spends the bulk of their week in calls, JIRA, and email. Technically comfortable but not a developer. Frustrated by the gap between SAP's internal tooling (designed for volume support) and the nuanced, relationship-driven work of delivery management. Needs fast, accurate answers to chargeability and pricing questions — often mid-call with a customer. Uses the agent as an AI-powered desk reference and request tracker.

**Goals:** Quickly confirm chargeability and price for a service, create and track AS requests without leaving the agent, generate O2I tickets with a single confirmation, process meeting notes without manual re-typing.

**Key Tasks:** R&R lookup → price lookup → email draft → create request → update request → generate O2I ticket → process OPS meeting notes → resolve inbox actions.

### Secondary Persona: The CDM Team Lead

Oversees a team of CDMs, reviews escalated Inbox actions, monitors open requests across the team. Does not use the agent daily but needs to trust that CDM-reported data is accurate and that invoicing steps are not being skipped.

**Goals:** Confidence that all chargeable AS work is tracked and invoiced; visibility into blocked or overdue requests.

### Other User Types

- **SAP Internal Operations / DevOps** — deploys and governs the agent on BTP; needs Joule-standard artifacts, health probes, and OTel data to operate it.

## Product Principles

1. **CDM confirms before commit** — the agent proposes (create request, O2I ticket, email); the human approves. No write operation happens without explicit CDM sign-off.
2. **Never hallucinate data** — all factual answers (chargeability, price, request data) come from tool calls. The agent does not answer from memory.
3. **Incremental, non-destructive** — meeting notes processing never overwrites existing decisions, risks, or owner history. It appends only.
4. **Joule-first** — all new artifacts (translation.json, serverCard.json, asset.yaml) are generated by Joule skills, not hand-authored.
5. **Adapt, don't rebuild** — the existing CAP backend and agent logic are preserved; only the Joule wrapper layer is new.

## Solution Architecture

**Architecture Overview:**  
Two-asset BTP solution: a Python FastAPI multi-agent service (`cdm-as-tracker-agent`) fronted by a CAP Node.js OData backend (`cdm-as-tracker-cap`). The agent runs on Joule Studio runtime; the CAP backend runs as a BTP application with HANA HDI persistence. XSUAA handles authentication for both assets.

**Key Components:**

- `cdm-as-tracker-agent` — Python FastAPI; Main Orchestrator + 6 specialist subagents (R&R, Pricing, Request Management, O2I, Client, Contract); 20 tools; Claude claude-opus-4-7 via Anthropic SDK; vector search for R&R PDFs and pricing Excel
- `cdm-as-tracker-cap` — CAP Node.js OData v4 service; persists AS requests, conversation memory, PendingActions, PersonalTemplates, PersonalNotes, and R&R document metadata in HANA
- `translation.json` / `serverCard.json` — MCP discovery artifacts; generated from live tool definitions
- `asset.yaml` — Joule runtime agent descriptor; ORD fields, model binding, probes
- `mcp-mock.json` — local test harness for all 20 tools

**Integration Points:**

- CAP OData (HTTP, read/write, per-request) — authoritative data store for all AS request data
- Anthropic API (HTTPS, per-message) — Claude claude-opus-4-7 for orchestration and subagent reasoning
- JIRA REST API (HTTPS, write, on CDM confirmation) — O2I invoice ticket creation
- XSUAA (HTTPS, per-request) — Bearer token validation via JWKS

**Deployment Environments:**

- Local dev: `.env` file, no XSUAA, CAP on port 4004, agent on port 8000
- BTP: XSUAA enforced, HANA HDI, Joule Studio runtime, OTel to SAP Cloud Logging

### Agent Extensibility & Instrumentation

**Agent Extensibility:**
- Each tool module under `app/tools/` is an extension point — new tools can be added without touching the orchestrator
- Subagents (R&R, Pricing, O2I, Client, Contract, Request Management) are independently extensible; new specialist agents can be registered in the orchestrator's routing table
- System prompt and tool list are loaded at startup; both can be overridden via environment variables for tenant-specific customisation

**Business Step Instrumentation:**
- All 7 milestones (see Milestones section) must emit structured OTel log events using the pattern: `[MILESTONE_ID].[achieved|missed]: [description]`
- Span attributes must include: `tool_name`, `session_id`, `cdm_email`, `duration_ms`, `outcome`
- Claude API spans must include: `input_tokens`, `output_tokens`, `cache_read_tokens`, `cache_write_tokens`

### Automation & Agent Behaviour

**Automation Level:** Autonomous agent with human-in-the-loop for write operations

**Actions the system performs without human approval:**
- R&R and pricing lookups (read-only vector search)
- Fetching AS records from CAP OData (read-only)
- Parsing raw customer emails to extract fields
- Processing meeting notes (read-only extraction, no writes until CDM approves patch)
- Routing to specialist subagents

**Actions that require human review or approval:**
- Creating a new AS request (`create_request`)
- Updating fields on an AS request (`update_record`)
- Sending a price-communication email (CDM reviews `render_action_panel` email-draft before sending)
- Generating and confirming an O2I JIRA ticket (`generate_o2i_ticket` → CDM approves → `confirm_o2i_invoiced`)
- Applying a meeting notes patch to stored JSON
- Proposing a dashboard layout change (`propose_layout_change`)

**Model:** Claude claude-opus-4-7 (Anthropic SDK, temperature 0.1, adaptive thinking, 10-iteration tool-use loop)

**Knowledge & data sources accessed:**
- R&R PDF documents — ingested, chunked, and vector-indexed; searched via `rr_lookup`
- AS Pricing List (Excel) — ingested and vector-indexed; searched via `price_lookup`
- CAP OData CDMService — AS requests, conversation memory, PendingActions, PersonalTemplates, PersonalNotes
- CAP OData AdminService — R&R document metadata, customer and contract registration

**Tools / connectors (20 total):**
- `rr_lookup` — vector search over R&R PDFs (read-only)
- `price_lookup` — vector search over pricing list (read-only)
- `parse_email` — extract AS request fields from raw email text (read-only)
- `draft_price_email` — generate price-communication email draft (read-only, output reviewed by CDM)
- `fetch_records` — query AS requests from CAP OData (read-only)
- `create_request` — create new AS request in CAP OData (write, requires CDM confirmation)
- `update_record` — update fields on AS request (write, requires CDM confirmation)
- `generate_o2i_ticket` — draft JIRA O2I invoice ticket body (read-only, output reviewed by CDM)
- `confirm_o2i_invoiced` — mark AS request as Invoiced after CDM confirms JIRA submission (write)
- `render_record_panel` — render record-card or status-timeline UI panel (read-only)
- `render_data_panel` — render table, KPI strip, checklist, or R&R source panel (read-only)
- `render_action_panel` — render email-draft, field-form, confirm-dialog, or ticket-ref panel (read-only)
- `render_notice_panel` — render reminder-banner notice (read-only)
- `get_layout` — read CDM's current dashboard layout (read-only)
- `propose_layout_change` — suggest layout change, renders confirm-dialog (write on CDM approval)
- `get_reminder_status` — check which reminder rules are firing for CDM's open requests (read-only)
- `route_to_agent` — delegate to Customer Orchestrator or Contract Subagent (internal routing)
- `surface_pending_action` — create PendingAction and push Inbox card (write)
- `resolve_pending_action` — mark PendingAction as responded or dismissed (write)
- `rename_assistant` — rename the assistant to a CDM-chosen name (write, persisted in session)

**Guardrails & fail-safes:**
- Never write to CAP OData without explicit CDM confirmation (confirmed via `confirm-dialog` panel or explicit user message)
- Never write email content directly — `draft_price_email` must be called first; content comes from its output only
- Never re-derive existing topic metadata in meeting notes — incremental extraction rule is enforced
- If `rr_lookup` returns `found:false`, ask 1–2 clarifying questions before retrying; never fabricate a service code
- If `rr_lookup` returns `too_broad:true` (>3 codes), ask narrowing questions before presenting results
- Token budget: adaptive thinking enabled; 10-iteration tool-use loop cap prevents runaway usage

## Non-Functional Requirements

### Performance
- **Latency**: Synchronous `/api/chat` p95 < 10s; streaming `/api/chat/stream` first-event < 2s
- **Throughput**: Designed for single-tenant CDM team usage (< 50 concurrent sessions)

### Reliability
- **Availability**: Inherits BTP application runtime SLA
- **Fallback**: If CAP OData is unreachable, agent returns a clear error message; no silent data loss

### Explainability
- **Traceability**: All factual answers cite the tool and source (R&R PDF filename, pricing row, CAP record ID)
- **Decision Logging**: All tool invocations logged with input summary, outcome, and duration via OTel
- **Uncertainty Communication**: If `rr_lookup` or `price_lookup` returns low-confidence results, agent surfaces this explicitly to CDM before acting

## Governance, Risk & Compliance

**Data Handling:**
- All AS request data stored in HANA on BTP — inherits BTP data residency and encryption at rest
- No PII beyond CDM email address (extracted from XSUAA JWT claims); not persisted beyond session context
- Conversation memory stored per session_id in CAP OData; retention policy to be defined by CDM operations team

**Approval Flows:**
- All write operations (create, update, O2I confirm, email send) require explicit CDM confirmation via the agent UI before execution

## Milestones

### M1: R&R Lookup Completed

- **Description**: CDM asks a chargeability question; agent returns 1–3 specific service codes from ingested R&R PDFs
- **Achieved when**: `rr_lookup` returns `found:true` with 1–3 service codes and a result panel is rendered
- **Log on achievement**: `M1.achieved: rr_lookup returned {n} service codes for query "{description}"`
- **Log on miss**: `M1.missed: rr_lookup did not return usable codes after {n} attempts for query "{description}"`

### M2: Pricing Confirmed

- **Description**: CDM receives EUR price for a service code and a draft price-communication email
- **Achieved when**: `price_lookup` returns a price and `draft_price_email` returns a draft; email-draft panel rendered
- **Log on achievement**: `M2.achieved: price confirmed for service_code={code}, draft email rendered for request={request_id}`
- **Log on miss**: `M2.missed: price_lookup returned no result for service_code={code}`

### M3: AS Request Created

- **Description**: A new AS request is recorded in the CAP OData backend
- **Achieved when**: `create_request` completes successfully and returns a new record ID
- **Log on achievement**: `M3.achieved: AS request created record_id={id} for customer={customer} cdm={cdm_email}`
- **Log on miss**: `M3.missed: create_request failed for customer={customer} reason={error}`

### M4: Request Lifecycle Updated

- **Description**: CDM updates status, notes, or fields on an existing AS request
- **Achieved when**: `update_record` completes successfully
- **Log on achievement**: `M4.achieved: record updated record_id={id} fields={fields}`
- **Log on miss**: `M4.missed: update_record failed record_id={id} reason={error}`

### M5: O2I Ticket Generated and Confirmed

- **Description**: JIRA O2I invoice ticket drafted, CDM approved, and AS request marked as Invoiced
- **Achieved when**: `confirm_o2i_invoiced` completes successfully after CDM approval
- **Log on achievement**: `M5.achieved: O2I confirmed record_id={id} ticket_ref={ticket_ref}`
- **Log on miss**: `M5.missed: O2I flow did not complete for record_id={id} — last step={step}`

### M6: Meeting Notes Processed

- **Description**: CDM pastes raw OPS meeting notes; agent extracts incremental structured JSON and generates 10 analysis sections
- **Achieved when**: Meeting notes processing completes and structured JSON with analysis is returned to CDM
- **Log on achievement**: `M6.achieved: meeting notes processed for client={client} topics={n} decisions={n} risks={n}`
- **Log on miss**: `M6.missed: meeting notes processing did not complete for client={client} reason={error}`

### M7: Inbox Action Resolved

- **Description**: A PendingAction card is surfaced to CDM Inbox and subsequently resolved
- **Achieved when**: `resolve_pending_action` completes with status `responded` or `dismissed`
- **Log on achievement**: `M7.achieved: pending action resolved automation_id={id} outcome={outcome}`
- **Log on miss**: `M7.missed: pending action not resolved automation_id={id} — surfaced but no response`

## Risks, Assumptions, and Dependencies

### Risks

- **orchestrator.py decomposition scope creep** — splitting 1,828 lines risks accidental behaviour changes. Mitigation: structural refactor only; run full test suite before and after.
- **translation.json schema drift** — tool schemas evolve after MCP artifacts are generated. Mitigation: generate from live tool definitions; re-run `mcp-translation-file` on any tool schema change.
- **Joule runtime version mismatch** — asset.yaml schema may differ between Joule SDK versions. Mitigation: use `sap-agent-bootstrap` to generate; do not hand-edit.

### Assumptions

- The existing XSUAA auth flow and CAP OData integration are correct and require no changes
- `claude-opus-4-7` remains available via SAP AI Core HAI proxy for BTP deployment
- The Joule Studio runtime supports Python FastAPI agents with custom endpoints beyond `/api/chat`

### Dependencies

- SAP Joule Studio runtime environment on BTP (target deployment)
- SAP AI Core HAI proxy for Anthropic API access in BTP
- HANA HDI container provisioned via BTP
- XSUAA service instance with correct scopes

## Appendix

### Glossary

- **CDM** — Customer Delivery Manager; SAP professional managing delivery for a set of customer accounts
- **AS** — Additional Services; chargeable services outside the standard delivery contract
- **R&R** — Roles and Responsibilities; SAP internal document defining chargeability of services by code

- **UMS** — Unified Metadata Store; Joule Studio service registry used for agent discovery and provisioning
- **ORD** — Open Resource Discovery; SAP standard for API and agent metadata exposure
- **PendingAction** — CAP entity representing an agent-initiated action awaiting CDM response in the Inbox
